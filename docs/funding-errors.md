# Funding error contract

`POST /api/invest/fund-invoice` is a capital-moving endpoint. It has a
dedicated error taxonomy so clients can make safe retry and remediation
decisions without parsing implementation-specific messages.

## Response shape

Every error produced by the funding route has this shape:

```json
{
  "error": {
    "code": "ESCROW_SUBMIT_FAILED",
    "message": "The escrow transaction could not be prepared. Please retry.",
    "requestId": "b1a7fdb4-9d89-4fc5-8ca1-4e4a2a54f1a0",
    "retryable": true
  }
}
```

`requestId` is the sanitized value generated by the request-ID middleware (or
the accepted proxy value) and is also returned in `X-Request-Id`. Support and
operators can use it to correlate the public response with structured logs.

## Codes and HTTP status

| Code | Status | Meaning | Retry |
| --- | ---: | --- | --- |
| `VALIDATION_ERROR` | 400 | The request fields are missing or malformed. | No |
| `MISSING_SME_ID` | 400 | The authenticated principal is incomplete. | No |
| `KYC_GATE_FAILED` | 403 | The principal is not permitted to move capital. | No |
| `ESCROW_NOT_FOUND` | 404 | No active escrow mapping exists for the invoice. | No |
| `FUNDING_CONFLICT` | 409 | The commitment conflicts with an existing write. | No |
| `ESCROW_SUBMIT_FAILED` | 502 | The escrow transaction could not be prepared or submitted. | Yes |
| `LEGAL_HOLD_ACTIVE` | 423 | The invoice is blocked by a legal hold. | No |
| `LEGAL_HOLD_STATUS_UNAVAILABLE` | 503 | The hold status could not be verified. | Yes |
| `FUNDING_INTERNAL_ERROR` | 500 | An unexpected failure occurred. | No |

The route never returns raw RPC, database, stack-trace, credential, or
configuration messages. The raw exception is retained only in structured
server logs and is correlated by `requestId`.

## Implementation rules

The router mounts `fundingErrorHandler` after its route declarations. Route
handlers throw typed `FundingError` values for expected failures; the
middleware owns status, code, safe message, retryability, logging, and request
correlation. Unknown errors are mapped to `FUNDING_INTERNAL_ERROR` and a safe
500 response.

This separation prevents a future funding branch from introducing an ad-hoc
`res.status(...).json(...)` response or leaking a dependency's error text. A
database uniqueness violation is deliberately normalized to `FUNDING_CONFLICT`.
Idempotent replays that return the existing commitment remain successful and
do not become conflicts.

## Client guidance

Clients should branch on `error.code`, record `error.requestId`, and retry only
when `retryable` is true. A 502 or 503 should use bounded exponential backoff.
Validation, authorization, missing escrow, legal-hold, and conflict responses
require a corrected request or operator action rather than an immediate retry.
